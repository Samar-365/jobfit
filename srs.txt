# 1. Project Overview

## 1.1 Purpose

JobFit is an AI-powered job application assistant that helps job seekers understand how their existing skills and experience relate to a specific job opening.

Job seekers often apply to multiple positions and repeatedly tailor their resumes, identify relevant skills, write cover letters, and track applications.

JobFit simplifies these tasks through local document processing, an open-weight Gemma model, evidence-based matching, and user-controlled document generation.

## 1.2 Problem statement

Existing AI resume tools often require users to upload personal career documents to external services. Some provide generic suggestions, opaque match scores, or resume rewrites that invent qualifications.

JobFit aims to provide:

- Private, local-first resume analysis.
- Transparent matching between a resume and a job description.
- Evidence-backed skill matching and gap analysis.
- Honest, tailored resume suggestions.
- Editable cover letter drafts.
- A simple job application tracker.

## 1.3 Product vision

**Help job seekers create stronger, more relevant applications without surrendering control of their personal career data.**

## 1.4 Target users

Primary users:

- College students.
- Fresh graduates.
- Software developers.
- Designers and other professionals.
- Career switchers.
- Active job seekers applying to multiple roles.

The MVP focuses on individual users rather than recruitment agencies or enterprise hiring teams.

## 1.5 Core differentiators

1. Gemma performs meaningful analysis rather than serving as a decorative chatbot.
2. Resume processing and model inference can run locally.
3. Match results explain which resume evidence supports each finding.
4. Missing qualifications are distinguished from skills that simply are not mentioned.
5. Generated content must remain grounded in the user's actual experience.
6. The application can work without a mandatory cloud LLM API.
7. Users control, edit, and approve their application documents.

The first release must include:

2. Job description input.

## 2.2 Features explicitly excluded from the MVP

Do not implement these unless the core workflow is already complete:

- Automated job scraping.
- Automatic job applications.
- Browser automation to submit applications.
- LinkedIn account integrations.
- Paid resume-scoring APIs.

- Complex user authentication.
- Cloud-based resume storage.
- Fine-tuning a model from scratch.
- Complex vector databases.
- Recruitment analytics for employers.

The goal is a complete product, not a large collection of unfinished features.

# 3. User Personas and User Stories

## Persona A: Final-year student

A student wants to understand whether their projects and skills align with a software developer role.

User story:

As a student, I want to compare my resume against a job description so I can identify relevant skills and understand what needs improvement.

## Persona B: Active job seeker

A job seeker applies to multiple companies and wants to avoid rewriting their resume from scratch each time.

User story:

As a job seeker, I want to create tailored resume suggestions and cover letter drafts from my existing experience so that I can prepare applications faster.

## Persona C: Career switcher

A professional wants to understand how their existing experience transfers to another field.

User story:

As a career switcher, I want JobFit to identify transferable skills and explain missing requirements without assuming that unmentioned skills are absent.

# 4. Functional Requirements

## FR-01: Dashboard

The dashboard shall provide:

- A welcome header.
- A prominent action to analyze a new job.
- Total applications tracked.
- Applications by status.
- Recent resume analyses.
- Saved job descriptions.
- Recent activity.
- A clear indication of local AI runtime availability.

All counts must come from actual stored records.

The application must not display fabricated match scores or hardcoded production metrics.

## FR-02: Resume Upload

Supported formats:

- PDF.
- DOCX.
- TXT.

Requirements:

- Validate file extensions and content where practical.
- Enforce file-size limits.
- Use safe filenames and local storage.
- Extract readable text.
- Display useful errors for unsupported or unreadable files.
- Preserve the original file where the user chooses to save it.
- Allow users to remove their saved resume and related local data.
- Never upload resume contents to a third-party LLM by default.

For image-based PDFs, OCR is optional for the MVP. If OCR is unavailable, explain the limitation clearly.

## FR-03: Resume Parsing

Extract structured information such as:

- Name, if present.
- Professional summary.
- Skills.
- Work experience.
- Projects.
- Education.
- Certifications.
- Employment dates.

Requirements:

- Separate document parsing from model inference.
- Treat extracted information as untrusted input.
- Do not assume every resume follows the same layout.
- Preserve the original text.
- Validate structured model output.
- Allow the user to correct parsing errors.
- Do not infer sensitive personal characteristics.

## FR-04: Job Description Input

Users shall be able to:

- Paste a job description.
- Enter the company name.
- Enter the role title.
- Save a job description for later.
- Reopen a saved analysis.

The application must work without internet access for its core analysis once the model and dependencies are installed.

## FR-05: Resume-to-Job Matching

JobFit shall analyze a resume against a job description.

The analysis should identify:

- Relevant technical skills.
- Relevant work experience.
- Relevant projects.
- Explicitly stated qualifications.
- Important job requirements not evidenced in the resume.
- Potentially transferable skills.
- Areas requiring clarification.

Every major finding should reference evidence from the resume or job description where possible.

The model must not assume that a skill is absent merely because it is not mentioned.

## FR-06: Match Score

The application may provide an indicative match score, provided that it is:

- Based on a documented, reproducible scoring method.
- Derived from explicit job requirements and resume evidence.
- Separated from the LLM's free-form opinion.
- Explained through visible component scores or contributing factors.
- Clearly described as an estimate, not a prediction of hiring success.

Do not describe the score as an ATS score unless a real ATS system and validated methodology are used.

Do not imply that the score predicts interview or hiring probability.

If a reliable scoring method cannot be completed on time, show a qualitative assessment instead.

## FR-07: Skill Gap Analysis

The application shall distinguish between:

- Skills explicitly supported by resume evidence.
- Requirements with partial or indirect evidence.
- Requirements not found in the supplied resume.
- Requirements that cannot be assessed confidently.

For each finding, display:

- Requirement.
- Resume evidence, if any.
- Explanation.
- Suggested next step.

Suggestions must not instruct users to claim skills or qualifications they do not possess.

## FR-08: Resume Tailoring

Users shall be able to select a section or bullet point and request an improved version.

Requirements:

- Preserve factual meaning.
- Improve clarity and relevance.
- Use job-description terminology only when supported by the user's actual experience.
- Never invent employers, degrees, certifications, projects, achievements, or metrics.
- Display original and suggested text side by side.
- Allow users to edit, accept, or reject suggestions.
- Preserve the original resume.
- Support copying or downloading the revised content.

## FR-09: Cover Letter Generator

Generate an editable cover letter draft based on:

- The user's resume.
- The selected job description.
- The company and role, if supplied.
- User-provided motivation or relevant context.

Requirements:

- Do not fabricate personal experiences.
- Do not invent company facts.
- Use placeholders when essential information is missing.
- Allow editing before export.
- Support plain-text or Markdown export.

## FR-10: Application Tracker

Users shall be able to:

- Add an application.
- Associate it with a company and role.
- Save the job description.
- Record the application date.
- Track status.
- Add notes.
- Update the status.
- Remove an application.

Suggested statuses:

- Saved.
- Preparing.
- Applied.
- Interview.
- Offer.
- Rejected.
- Withdrawn.

The tracker must use local persistent storage.

## FR-11: Local AI Runtime

Use Gemma through Ollama.

Initial model candidate:

`gemma3:1b`

Requirements:

- Configurable model name.
- Local inference for core analysis.
- Clear model health status.
- Graceful handling of unavailable Ollama.
- Inference timeouts.
- Schema validation for model output.
- Controlled retry for malformed output.
- No fake successful responses.
- No mandatory cloud LLM API key.

Test model performance on the developer's available hardware before considering a larger model.

## FR-12: Privacy and Data Management

Users must be able to understand:

- Where resume files are stored.
- Which model processes the documents.
- Whether any external services are enabled.
- How to delete stored documents and application records.

By default:

- Store files locally.
- Store metadata in SQLite.
- Use local Ollama inference.
- Avoid sending document contents to telemetry providers.
- Keep secrets out of source control.

## FR-13: Export

The MVP shall support:

- Copying generated resume suggestions.
- Downloading a revised resume in a practical format where feasible.
- Exporting cover letter text.
- Exporting application tracker data as CSV.

DOCX generation is preferred if it can be implemented without destabilizing the core workflow.

# 5. Non-Functional Requirements

## NFR-01: Reliability

- Invalid model output must not corrupt saved data.
- Model failures must be visible.
- The application must not fabricate analysis.
- Saved applications must persist across restarts.
- Generated documents must remain editable.

## NFR-02: Security

- Validate uploaded file types and sizes.
- Prevent path traversal.
- Do not execute uploaded files.
- Treat document contents as untrusted data.
- Guard against prompt injection within resume and job-description text.
- Never expose secrets or unnecessary filesystem paths.
- Do not send private documents to third-party services without explicit disclosure and consent.

## NFR-03: Maintainability

Separate:

- File parsing.
- AI inference.
- Matching logic.
- Resume editing.
- Application tracking.
- Storage.
- API routes.
- Frontend feature modules.

Use typed schemas, environment-based configuration, and automated tests.

## NFR-04: Usability

- Keep the main workflow understandable to nontechnical users.
- Show actionable explanations rather than raw model output.
- Use clear loading and error states.
- Provide an accessible, responsive layout.
- Keep editing and approval under user control.

## NFR-05: Performance

Measure actual inference latency and document the model, hardware, and test set.

Do not promise a fixed response time or accuracy before measurement.

Consider Render only if a hosted demo materially improves judging.

Important distinction:

A hosted web application is not automatically local-first. Clearly explain which components run on the hosted server and which run locally. Do not promise local processing if resume files are sent to a remote backend.

## Optional target: Sentry

Use Sentry only if it can be configured safely to capture actionable errors without leaking resume text, contact details, or job application content.

## Integration rule

Do not add a partner technology solely for its logo.

Every claimed integration must work, be documented, and contribute to the project.

Prioritize the core product and Gemma over optional integrations.

# 10. Testing Strategy

## Functional tests

Test:

- Valid PDF and DOCX resumes.
- Invalid and oversized uploads.
- Unreadable documents.
- Empty job descriptions.
- Missing resume fields.
- Malformed model responses.
- Ollama unavailable.
- Resume analysis persistence.
- Resume suggestion editing.
- Cover letter generation.
- Application status changes.
- File and record deletion.
- Export functionality.

## Matching-quality tests

Create a small synthetic dataset of resume/job-description pairs with manually documented evidence.

Evaluate:

- Whether relevant skills are identified.
- Whether matching evidence is accurate.
- Whether missing requirements are described cautiously.
- Whether the model invents experience.
- Whether the explanation matches the source documents.

Do not claim the matching score predicts hiring success.

## Privacy tests

Verify that:

- Core inference uses local Ollama.
- Resume content is not sent to external LLM APIs.
- Sensitive document content is not written to logs.
- Deletion removes the appropriate local files and records.
- Optional external integrations are clearly disclosed.

## Benchmark report

Record:

- Hardware.
- Model and configuration.
- Number of test cases.
- Latency.
- Matching-quality observations.
- Failure cases.
- Known limitations.

Report only actual measurements.
